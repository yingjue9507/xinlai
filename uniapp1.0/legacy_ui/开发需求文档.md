# 开发需求文档（增量）

更新时间：2025-11-28

## 功能：礼簿列表示例项交互安全优化

- 背景：用户在列表点击示例项（如 `ledger_001`）会进入详情页请求后端，返回“礼簿不存在或无权限访问”的弹窗，体验不佳；且再次点击无提示、不跳转。
- 目标：防止示例项误触导致无权访问弹窗；进入页面先清理示例项并显示加载占位，待真实数据渲染。

### 需求说明
- 页面加载阶段：
  - 在 `DOMContentLoaded` 后立即显示“加载礼簿中”占位，并清空示例列表内容。
- 点击委托拦截：
  - 对匹配示例 ID 规则 `^ledger_\d+$` 的项进行拦截，提示“这是示例项，无法查看详情。请点击真实礼簿。”，不进行跳转。

### 实现范围
- 文件：`新版界面/ui_pages_618336854786/P-LEDGER_LIST.html`
- 新增方法：`showInitialLoadingState()`
- 更新方法：`initListClickDelegation()` 增加示例项 ID 拦截逻辑

### 验收标准
- 进入“我的礼簿”时，先出现加载占位，示例项不再可点击。
- 点击示例项时被拦截并提示，不会跳转详情页。
- 真实礼簿项点击后能正常跳转至 `P-LEDGER_DETAIL.html?ledger_id=真实ID`。

### 兼容与安全
- 不影响真实数据渲染逻辑与搜索功能。
- 提示文案与历史处理逻辑一致，避免用户误解为权限问题。

## 功能：记录方向字段与保存逻辑修复（收/送出）

- 背景：用户反馈“点击送出保存后，详细记录列表转变成收到状态”。数据库 `Record` 模型未存储收/送出方向，导致前端无法按记录真实方向展示。
- 目标：为每条记录持久化方向字段（`recordType`），确保详情页等列表正确展示“收到/送出”。

### 需求说明
- 后端：
  - `Record` 增加字段：`record_type`（String，默认值 `"received"`）。
  - 接口 `POST /api/records`：读取请求体中的 `recordType`，兼容旧值映射（`sent/given` → `sent`，其他 → `received`），并保存到数据库。
  - 数据迁移：新增迁移 `add-record-type` 并应用到 SQLite 开发数据库。
  - 保存归属逻辑调整：当用户在礼簿详情页保存记录时，始终归档到当前礼簿（按 `ledgerId`），不因 `recordType` 与礼簿类型不一致而切换或创建礼簿。
  - 统计逻辑调整：联系人统计改为按 `recordType` 计算 `totalReceived/totalGiven`，不再依赖礼簿类型推断。

### 实现范围
- 文件：
  - `backend/prisma/schema.prisma` — 新增 `recordType` 字段（String）。
  - `backend/src/routes/record.routes.ts` — 创建记录时保存 `recordType`。

### 验收标准
- 在“新增记录”页选择“送出”，保存后按接口返回数据查看详情页记录，方向应为“送出”。
- 旧记录默认为“收到”，如需调整需在运维侧或前端提供修正入口。
 - 在某一个礼簿详情页（如“王二”）保存“送出”记录后，记录应归属于该礼簿，不会被切换到新建的默认礼簿。

### 兼容与建议
- 前端详情页及联系人记录列表优先使用 `recordType` 渲染方向，避免仅依赖 `ledgerType`。
- 后续增加端到端测试，覆盖保存与展示方向一致性。

### 易用性增强
（废弃）不再在保存时依据方向自动创建或切换礼簿，避免与用户当前页面上下文冲突。

## 功能：前端显示修正（按记录方向展示正负与颜色）

- 背景：用户反馈“送出可以保存，但在列表仍算到收到里，未显示负数红色”。此前列表渲染依据 `ledgerType` 推断方向，未使用真实的 `recordType`。
- 目标：在礼簿详情页与联系人往来页，按每条记录的 `recordType` 显示金额的符号与颜色：`received` 显示为 `+` 且绿色；`sent` 显示为 `-` 且红色。

### 需求说明
- 前端：
  - `P-LEDGER_DETAIL.html`：记录列表项的金额与颜色基于 `record.recordType` 渲染，`received`→`+`/`text-success`，`sent`→`-`/`text-danger`。
  - `P-CONTACT_RECORDS.html`：
    - 卡片样式、方向图标与标签基于 `record.recordType` 渲染（收到=绿，送出=红）。
    - 统计汇总 `totalReceived/totalGiven/balance` 基于 `record.recordType` 计算，不受礼簿类型影响。

### 实现范围
- 文件：
  - `新版界面/ui_pages_618336854786/P-LEDGER_DETAIL.html` — 列表项金额符号与颜色切换。
  - `新版界面/ui_pages_618336854786/P-CONTACT_RECORDS.html` — 卡片与统计逻辑切换到 `recordType`。

### 验收标准
- 在礼簿详情页新增并查看一条 `sent` 记录：金额前缀显示 `-`，颜色为红色；`received` 记录为 `+` 且绿色。
- 在联系人往来页：列表方向（图标/标签/颜色）与金额符号正确；统计汇总中“收到”为正向累计，“送出”为负向累计，结余为两者差值；结余为负时显示红色。

### 兼容与建议
- 若存在旧记录无 `recordType` 字段或为空，按默认 `received` 处理，后续可提供数据修正入口。
- 后端按需可提供签名统计字段（如 `totalReceived/totalSent/netAmount`），当前前端已可通过 `recordType` 自行计算。

## 功能：接口返回字段与统计口径调整（recordType）

- 背景：前端已统一按 `recordType`（收到/送出）渲染金额符号与颜色，但部分接口未返回该字段，且统计口径仍以 `ledgerType`（我办事/参加别人的事）推断，导致展示与统计不一致。
- 目标：所有返回记录的接口补充 `recordType` 字段；统计汇总统一按 `recordType` 计算“累计收到/累计送出/结余”。

### 需求说明
- 接口返回字段补充：
  - `GET /api/records/recent`：在每条 `record` 中新增 `recordType` 字段。
  - `GET /api/records/contact/:contactName`：在每条 `record` 中新增 `recordType` 字段。
- 统计口径调整：
  - `GET /api/records/stats`：使用 `recordType` 计算 `totalReceived/totalGiven/balance`，忽略 `ledgerType` 推断。
  - `GET /api/ledgers/home-stats`：遍历各礼簿的记录，基于 `recordType` 统计收/送与结余。

### 实现范围
- 文件：
  - `backend/src/routes/record.routes.ts` — `recent/contact/stats` 接口字段与统计调整。
  - `backend/src/routes/ledger.routes.ts` — `home-stats` 统计按 `recordType` 调整。

### 验收标准
- 首页“近期动态”卡片能正确显示收到为 `+`/绿色，送出为 `-`/红色（源于返回的 `recordType`）。
- 联系人往来列表方向与统计均与 `recordType` 一致，无因礼簿类型造成的误判。
- 首页统计“累计收到/累计送出/结余”与联系人统计一致，按照 `recordType` 口径计算。

### 兼容与注意
- 旧数据无 `recordType` 的情况，默认视为 `received`；后续可提供数据修正脚本。
- `ledgerType` 仍保留其礼簿语义（如“我办事/去随礼”），但不参与单条记录方向或统计的判定。
## 功能：登录功能开发态策略与测试账号

- 背景：需要在不接入真实短信的前提下完成登录流程联调与测试；同时希望使用极简测试账号。
- 目标：开发环境允许测试手机号 `123` 与验证码 `123` 直接登录；其他手机号继续按常规规则验证；前端与后端口径一致，后续可无缝切换为真实短信校验。

### 需求说明
- 后端接口（开发态）：
  - `POST /api/auth/send-code`：
    - 当 `phoneNumber === '123'` 时固定返回验证码 `123`；其他手机号返回随机 6 位验证码（开发态仅用于展示）。
  - `POST /api/auth/login`：
    - 允许手机号 `123` 与验证码 `123` 登录；其他手机号在开发态放宽（保留 6 位数字格式校验）。
    - 登录成功后按手机号“查找或创建”用户，并更新 `lastLoginDate`。
    - 返回包含 `token` 与 `user` 基本信息。
- 前端（静态页面）：
  - `P-LOGIN.html` 中的校验放宽：
    - `validatePhone` 允许 `123` 作为测试号；否则按中国大陆 11 位手机号正则校验。
    - `validateVerificationCode` 允许 `123`；否则要求 6 位数字。
  - 登录成功后将 `token` 与 `user` 写入 `localStorage`，后续页面通过 `Authorization: Bearer <token>` 访问后端。

### 实现范围
- 文件：
  - `backend/src/routes/auth.routes.ts` — 放行测试账号与验证码；校验规则支持测试号。
  - `新版界面/ui_pages_618336854786/P-LOGIN.html` — 放宽前端校验以支持测试号与验证码。

### 验收标准
- 使用手机号 `123` 与验证码 `123` 能成功登录并进入首页。
- 登录后所有受保护接口（礼簿/记录/公告等）均可正常访问，接口携带 `Authorization` 头部。
- 非测试号仍需满足原有格式校验；生产态需按照真实短信验证要求（当前暂不接入）。

### 后续计划与注意
- 后续接入真实短信服务时：
  - 新增验证码存储表（手机号/验证码/过期时间/状态），并在登录时进行校验与作废。
  - 增加发送频率限制与风控（同手机号/同 IP 限流、失败次数限制）。
  - 切换生产数据库（Postgres），并在 `.env` 中配置 `DATABASE_URL`。
